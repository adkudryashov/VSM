## 2. Главное архитектурное изменение

**telemt_panel уехала с открытого порта на 443 домена панели по случайному
32-символьному префиксу пути.**

Было: панель слушала `0.0.0.0:9444` и терминировала TLS своим сертификатом.
Снаружи это выглядело как админ-форма с валидным сертификатом на нестандартном
порту — сканеру хватало одного соединения, чтобы классифицировать сервер, и вся
работа по маскировке порта telemt теряла смысл.

Стало: панель слушает `127.0.0.1`, TLS терминирует nginx, наружу открыты только
443 и порт telemt. Побочно исчезла необходимость выдавать панели ACL на
приватный ключ Let's Encrypt — процесс, смотрящий в интернет, ключ больше не читает.

Три следствия, которые надо помнить:

1. **Блок доступа живёт в `sites-enabled`** и не переживает патч 3x-ui-pro — тот
   вычищает каталог целиком. Маска в `conf.d` переживает. Поэтому пункт 4
   переприменяет оба и называется «Восстановить конфиги nginx».
2. **Панель не умеет работать из подкаталога**: в её HTML зашиты `<base href="/">`
   и `window.__BASE_PATH__=""`. Лечится `sub_filter` — поддержка префикса в
   приложении есть, ему надо лишь сообщить непустое значение. Обязателен
   `proxy_set_header Accept-Encoding ""`, иначе sub_filter не правит сжатый ответ.
3. **Миграция старых установок** делается тем же пунктом 4: если `PANEL_PREFIX`
   в конфиге нет, он создаётся и дописывается.

## 3. Пересборка nginx — починена и принята на живом сервере

### Что было

```
./configure: error: the HTTP XSLT module requires the libxml2/libxslt
libraries. You can either do not enable the module or install the libraries.
```

Скрипт берёт `configure`-флаги из `nginx -V` и переводит динамические модули в
статические, **но не ставил их зависимости сборки**. Это причина, по которой
пересборка не проходила у владельца ни разу. Провал был безопасным:
`set -euo pipefail` обрывал работу до подмены бинарника.

### Что сделано

**Отбор модулей по факту, а не по списку.** Пять необязательных модулей
(`http_xslt`, `http_image_filter`, `http_perl`, `http_geoip`, `mail`)
вырезаются из `BUILD_ARGS`, если их директив нет в **эффективном** конфиге
(`nginx -T`, а не один файл). Если директива есть — модуль остаётся, а его
dev-пакет доставляется. Направление ошибки выбрано намеренно: греп идёт по
всему выводу, включая комментарии, и без правой границы слова, так что
`upstream image_filter_backend` засчитается за использование. Лишний пакет
дешевле упавшего `nginx -t` после подмены бинарника.

Список из прежней редакции этого документа был неполон трижды. `http_geoip`
тоже требует `libgeoip-dev`; `--with-mail` нельзя снимать без парного
`--with-mail_ssl_module`; и главное — Ubuntu собирает geoip **дважды**, как
http-модуль и как stream-модуль, оба динамические. Первая редакция таблицы
знала только http-версию, и сухой прогон на стенде показал
`--with-stream_geoip_module` в итоговых флагах без `libgeoip-dev`: сборка
упала бы так же, как на xslt, только на несколько минут позже. Приставка
`stream` при этом не повод оставлять модуль — обязательны лишь `--with-stream`,
`--with-stream_ssl_module` и `--with-stream_ssl_preread_module`, они проверяются
отдельно, а geoip к разбору SNI отношения не имеет.

Теперь таблица покрывает все модули штатного nginx, которым нужны внешние
библиотеки сборки: xslt, image_filter, perl и geoip обеих версий. Остальным
хватает openssl, pcre2 и zlib.

**`stream` защищён явно.** Перед `./configure` проверяется наличие
`--with-stream`, `--with-stream_ssl_module`, `--with-stream_ssl_preread_module`;
их отсутствие — `die` до единого изменения в системе. На них держится
SNI-роутинг 443 на панель и REALITY.

**OpenSSL теперь устанавливается.** Этап 1 делал `make`, но не `make install`,
поэтому `/opt/openssl-3.5` не появлялся никогда. Итог был тихий: SUMMARY
советовал `PATH` на несуществующий каталог, а `_pq_openssl_bin` в
`menu_telemt.sh` искал `/opt/openssl-3.5/bin/openssl` — и PQ-часть пункта 5
оставалась «Пропущено» даже после успешной пересборки. Добавлен
`make install_sw` с проверкой запуском бинарника. Порядок важен: установка
обязана пройти **до** этапа 2, потому что nginx с `--with-openssl=<исходники>`
делает в том же дереве `make clean` и пересобирает OpenSSL под себя.

**C14 закрыт.** `systemctl stop nginx` по инварианту 2 уносил `telemt` и
`telemt-panel`, а поднимался только nginx: после 20–40 минут печаталось
зелёное «Готово» над мёртвым прокси. Теперь список активных служб снимается
**до** остановки, поднимается в обеих ветках (успех и откат), проверяется
фактом через `wait_until`, а итоговая рамка при неподнявшейся службе краснеет
и скрипт возвращает 1. Пункт 9 меню читает этот код и печатает фактическое
состояние трёх служб.

**Откат стал полным.** Бэкапился бинарник и `modules-enabled`, но не
`nginx.conf`, из которого скрипт удаляет строку `load_module
ngx_stream_module.so` — прежнему, динамическому, бинарнику она необходима.
Откат оставлял сервер без `stream`, то есть без разбора SNI на 443. Добавлен
`nginx.conf.pre-openssl35.bak`.

**`DRY_RUN=1`** печатает решения отбора и итоговые флаги `./configure`, ничего
не меняя. Операция необратимая и на 20–40 минут — её решения стоит увидеть
заранее. Окупился сразу: `stream_geoip` нашёлся именно им, до того как была
потрачена хоть минута сборки.

### Побочная находка: сверка TLS врала о расхождении

Замечена при снятии слепка перед прогоном. `_tls_dump` закрывал stdin голым
`echo |`, а блок `SSL-Session`, где лежат `Protocol` и `Cipher`, печатается
при закрытии соединения — `s_client` успевал выйти раньше. Замер на стенде,
по 8 попыток на порт: полными оказались **5 дампов из 8 на каждом порту**.

Дефект был не в пустых полях, а в том, что из них следовало: пустое значение
на одном порту против заполненного на другом читается в цикле сравнения как
РАСХОЖДЕНИЕ. При независимых 5/8 ровно один порт обрезается почти в половине
запусков — пункт регулярно печатал две красные строки и советовал чинить
исправную маскировку. Зеркало того же класса дефектов, только со знаком минус:
рапорт не по факту.

Лечится паузой перед EOF — `{ echo; sleep 1; }` вместо `echo`. На стенде дало
8 полных дампов из 8 на обоих портах. Та же пауза добавлена в PQ-пробу.

### Ещё четыре дефекта, найденных прогонами на стенде

**Свой openssl подхватывал системные библиотеки.** `make install_sw` отработал,
`/opt/openssl-3.5/bin/openssl` лёг на место исполняемым — и не запускался:
`version 'OPENSSL_3.5.0' not found`. У бинарника не оказалось ни RPATH, ни
RUNPATH, и загрузчик брал системные `libssl.so.3` / `libcrypto.so.3` версии
3.0.13. Лечится двумя `-Wl,-rpath` на этапе `Configure` (`lib64` и `lib`).
`LD_LIBRARY_PATH` не годится: `_pq_openssl_bin` вызывает бинарник **голым**,
без окружения. Поймала это проверка запуском — по коду возврата `make` всё
выглядело сделанным.

**Повторный запуск делал откат ломающим.** `cp` клал в бэкап уже пересобранный
статический бинарник, а бэкап `modules-enabled` оставался с первого запуска.
Откат вернул бы статический бинарник **вместе** с директивами `load_module` —
«module already loaded», nginx не стартует, за ним по инварианту 2 ложится
telemt. Теперь оба бэкапа не перезаписываются, если уже есть: они обязаны
описывать состояние до ПЕРВОЙ пересборки. Бэкап `nginx.conf`, наоборот,
перезаписывается намеренно — он нужен только внутри текущего запуска, а старая
копия затёрла бы правки, сделанные между прогонами.

**Молча терялись сторонние модули.** В `modules-enabled` на стенде лежало
восемь файлов, семь из них — `nginx-extras`: `echo`, `subs_filter`, `geoip2`
(http и stream), `auth_pam`, `dav_ext`, `upstream_fair`. В `nginx -V` их нет
вовсе — Debian собирает их отдельными пакетами против ABI, а не флагами
configure, поэтому разбор флагов их не видел. Скрипт вычищал каталог целиком.
Терять их незачем: `--with-compat` сохраняется, и все семь проверенно грузятся
в пересобранный nginx. Теперь снимается только конфликтующий — тот, что стал
статическим, — и находится он разбором жалобы `nginx -t`, а не списком имён.

**`grep -r` не ходит по симлинкам.** `/etc/nginx/modules-enabled/` состоит из
ссылок на `/usr/share/nginx/modules-available/`. Имя модуля из жалобы
разбиралось верно, файл не находился, функция сдавалась не сняв ничего.
Перечисление глобом эту разницу снимает.

### Ловушка `pipefail`, встреченная в этом файле трижды

`producer | head -1` и `producer | grep -q`: потребитель выходит на первой
строке, producer получает SIGPIPE, конвейер возвращает 141 **при фактическом
успехе**. С `|| var=""` это затирает верный результат молча. Встречена в
`has_arg`, в разборе имени модуля и в проверке собранного бинарника. Везде
убрана: сравнение через развёрнутую строку, снимок в переменную, первая строка
через `${var%%$'\n'*}`. Ни одна не выстрелила на стенде — вывод помещался в
буфер трубы, — но полагаться на размер буфера не стоит.

### Известная дыра рядом, не чинилась

Флаги `--add-dynamic-module=<путь>` фильтр не трогает: они не содержат
`=dynamic` и проходят мимо ветки конвертации. Модуль соберётся в `objs/`, но
устанавливается только бинарник — значит модуль, собираемый ИЗ ИСХОДНИКОВ
рядом с nginx (brotli по такой схеме), после пересборки не появится. Это не то
же самое, что модули `nginx-extras` выше: те приходят готовыми `.so` из
пакетов и теперь сохраняются. На стенде флагов `--add-dynamic-module` нет.

### Артефакт MTProxyL «Установить PQ OpenSSL (из Release)» — не подходит

Проверено по их `.github/workflows/build-pq-nginx.yml`: **в сборке нет модуля
`stream`**, только http-модули. Подстановка их бинарника убьёт маршрутизацию 443
целиком. Плюс у них зашит `--prefix=/opt/mtproxyl-nginx`, и их nginx — отдельная
служба, а не замена системной: PQ достался бы их стеку, не нашему.

Заимствовать стоит не функцию, а идею: собирать **свой** артефакт в GitHub
Actions с нашим набором модулей. Снимет и 20–40 минут компиляции, и `apt-mark
hold`, который сейчас останавливает security-обновления nginx. Workflow-ов в
репозитории пока нет.

Автоопределение убрано из меню. Домены спрашиваются всегда, пустой или
совпадающий ввод отклоняется правилом из `ask_domains`.

### Проверка CPU снималась только в одном пути из трёх

`check_cpu` в `x-ui-latest.sh` ищет «QEMU» в `/proc/cpuinfo` и делает `exit 1`.
Снималась она лишь при установке панели, а **удаление панели** и **установка

Сведено в `xui_installer_fetch`: качает, сверяет отпечаток, снимает проверку.
Снятие подтверждается **фактом** — прежний код правил файл только при точном
`grep -q '^check_cpu$'`, а иначе молчал и ехал падать. Новый шаблон переживает
отступ; `check_cpu || true` он намеренно не ловит и обязан сказать об этом
вслух. В `x-ui-patch.sh` проверки CPU нет — сверено по тексту.

### Отпечатки сторонних установщиков — сделано

Решение владельца из §6 закрыто для путей 3x-ui-pro. Версии не фиксируются, как

### Пересборка nginx ломала удаление панели

Найдено при проверке. `apt-mark hold`, который ставит пересборка, делает
невозможным `apt purge nginx`: захолженный `nginx-full` зависит от `nginx`, и
apt отказывается разрешать конфликт — `apt-get -s purge nginx nginx-common`
возвращает 100. Установщик автора в режиме `-uninstall` делает именно purge.

Связь двух пунктов меню нигде не была записана, и узнать о ней можно было
только попробовав. Удаление панели теперь снимает фиксацию само и проверяет,
что она снялась; в SUMMARY пересборки про это сказано.

## 3б. AmneziaWG 2.0 / 3.0 — добавлен

Пункт 4 главного меню. Стоит рядом со стеком и с ним не пересекается: nginx,
сертификаты и порты панели не трогаются, занимается один UDP-порт.

### Почему именно этот источник

3.0 (диапазоны H1-H4, пакеты I1-I5, `HeaderProtectionKey`, рандомизированные
тайминги) подаётся контейнерами `Vadim-Khristenko/awg-containers-and-tools`
через UAPI-сокет демона. Выбраны как единственный **готовый** путь: ни один из
трёх сторонних установщиков 3.0-обфускации не даёт.

Отвергнуты — разбор от 7 августа по исходникам, а не по README:

| Источник | Что даёт | Почему не взят |
|---|---|---|
| `wiresock/amneziawg-install` | `Jc/Jmin/Jmax`, `S1`-`S4`, `H1`-`H4` | Ни ключей 3.0, ни пакетов `I1`-`I5` — набор эпохи 1.5, ниже нашей 2.0. К системе при этом аккуратнее всех: политику UFW не трогает, правила кладёт в `PostUp`/`PostDown` самого интерфейса |
| `bivlked/amneziawg-installer` | То же плюс `I1` | «3.0» у него — версия модуля из PPA, а не обфускация: `HeaderProtectionKey` не ставится сознательно. Плюс `apt full-upgrade` (не отключается флагом `--no-tweaks`), purge `snapd`/`unattended-upgrades`/`packagekit`, две перезагрузки из скрипта, `ufw limit 22/tcp`. Рассчитан на чистый VPS под один VPN |
| `Any-Tech-ARCHITECT` | — | Не установщик, а генератор параметров |

Прежняя редакция этого абзаца утверждала, что 3.0 «штатным серверным
инструментом не подаётся, `awg setconf` этих ключей не знает». **Это неверно**:
эталонная проверка от 6 августа показала обратное — `amneziawg-tools
v3.0.20260805` из `ppa:amnezia/ppa` принял конфиг целиком, и `awg show` вывел
`header protection key` и `content padding addition`. Путь «PPA + DKMS, ключи
3.0 пишем сами» существует. Переезжать на него сейчас незачем — контейнерный
путь принят на стенде, — но причина выбора должна звучать честно.

Про UFW у `bivlked` прежде было сказано, что он «убил бы стек молча». Точнее:
при **уже включённом** UFW он только добавляет правила и стек не режет; опасен
случай выключенного UFW, где ставится `default deny incoming` и разрешаются
лишь SSH и порт VPN. Перед включением он спрашивает подтверждение, так что
«молча» — неверно.

### 2.0 берётся оттуда же

Отдельный установщик под 2.0 (`wiresock`: PPA плюс модуль ядра через DKMS)
рассматривался и отвергнут. Он рабочий, но это второй механизм установки со
своей поверхностью конфликтов — сборка модуля против ядра, apt-репозиторий,
свои правила NAT, — ради версии, которая тем же семейством контейнеров уже
покрыта образом `vaiprog/amnezia-wg-2`. Один проверенный путь на обе версии
дешевле двух.

**Версии различаются НЕ пакетами I1-I5.** Первая редакция проверки считала
`I1` признаком 3.0 и была неверна: `awg-tool gen --version 2.0` тоже выдаёт
I1-I5 — проверено выводом на обеих версиях. Отличают 3.0 ключи
`HeaderProtectionKey`, `ContentPaddingAddition` и рандомизированные тайминги,
которых в 2.0 нет вовсе. Ошибка здесь дорогая: образ 2.0 отвергает 3.0-ключи с
`errno=-22` и молча уходит в цикл перезапуска — так и поймали на стенде.

### Клиентские конфиги выдавались с раздельным туннелем

Самый дорогой из найденных. Умолчание `awg-peer` для `AWG_CLIENT_ALLOWED` —
`<подсеть туннеля>/24, <DNS>/32`, а не `0.0.0.0/0`, как обещает комментарий в
их же compose. Меню этот параметр не передавало, и каждый выданный конфиг
получал **раздельный туннель**: клиент подключается, рукопожатие проходит, а в
интернет не идёт ничего — ни один реальный адрес в `AllowedIPs` не попадает.

Снаружи это выглядит как «VPN не работает», и причина видна только в одной
строке конфига. Поймано владельцем при переносе конфига в mihomo. Формат
оказался ни при чём: mihomo поддерживает и `s3`/`s4`, и диапазоны `h1`-`h4`,
и пакеты `i1`-`i5`.

### Утечка IPv6 закрыта заглушкой

Прежняя редакция говорила: «`::/0` не завернул бы трафик, а похоронил его» — и
делала из этого вывод не добавлять его вовсе. Вывод был неверный: **похоронить
и есть цель**. Без `::/0` клиент на сервере с IPv6 ходит по нему напрямую к
своему провайдеру в обход туннеля и светит настоящий адрес. С `::/0` трафик
IPv6 уходит в туннель, где адреса IPv6 нет, и гибнет там.

В `AllowedIPs` теперь `0.0.0.0/0, ::/0`. Серверную часть это не трогает вовсе:
`::/0` живёт только в клиентском конфиге, у пира на сервере разрешён по-прежнему
один адрес IPv4.

Проверено на стенде обеими сторонами — эталонный клиент в отдельном netns,
которому специально дали рабочий IPv6 наружу через veth и NAT66:

| | до туннеля | после туннеля |
|---|---|---|
| `ping -6 2606:4700:4700::1111` | 2/2 прошло | 0/2, 100% потерь |
| `ping -4 1.1.1.1` | — | 3/3 через туннель |

То есть утечка существовала и закрылась, а IPv4 не пострадал. `awg-quick`
принял `::/0` без единой жалобы: `ip -6 route add ::/0 dev <iface> table 51820`.

**Цена названа вслух:** связности по IPv6 у клиента не будет вовсе. Решение
владельца от 8 августа 2026 — предпочесть отсутствие утечки отсутствию IPv6.

Полноценный dual-stack технически возможен: entrypoint разбивает `AllowedIPs`
по запятым и для `[Peer]`, и для адреса интерфейса, а демон принимает несколько
строк `allowed_ip` (проверено, `errno=0`; запятая в одной строке — `errno=-22`).
Упирается он в другое: `awg-peer` пишет пиру **один** адрес, и восстановление
из `peers.d` при перезапуске контейнера отдаёт демону одну строку `allowed_ip`.
Второй адрес перезапуск не переживёт. Значит dual-stack требует своего
управления пирами вместо их инструмента — отдельная работа, не сделана.

**Отдельно, для тех, кто будет вокруг `awg-peer` что-то писать:** конфиг он
печатает в stdout, а свои события журнала — в stderr. Слитые вместе через
`2>&1` они попадают внутрь конфига, и `awg-quick` отвечает невнятным
`Configuration parsing error`. Поймано в этом же прогоне на собственном тесте.

### Резолвер в контейнере из туннеля недостижим

Второй дефект той же выдачи конфигов. В каждый конфиг вписывался
`DNS = 172.29.172.254` — адрес контейнера-резолвера на docker-мосту. Но сервер
работает в **host-режиме** и на этом мосту не стоит: измерено на стенде, из
туннеля адрес недостижим — ни пинга, ни ответа на запрос, — хотя с самого
хоста резолвер отвечает нормально.

Снаружи это выглядит хуже всего: туннель поднимается, рукопожатие проходит,
трафик по IP идёт, а имена не разрешаются. Владелец поймал это на mihomo,
который с `remote-dns-resolve: true` резолвил через туннель и помечал прокси
недоступным. Смена на `remote-dns-resolve: false` вылечила — то есть дело было
именно в резолвере, а не в туннеле.

Клиентам теперь выдаётся публичный `1.1.1.1`. Запрос всё равно уходит **внутри
туннеля**, то есть местному провайдеру не виден — ради чего резолвер и
задумывался. Проверено: имена резолвятся, health-check
`https://www.gstatic.com/generate_204` отдаёт 204 за 0.3 с.

**Механизм найден: это защита самого Docker.** В таблице `raw` стоит ровно одно
правило, и поставил его Docker 29:

```
-A PREROUTING -d 172.29.172.254/32 ! -i br-ca9329b88f80 -j DROP
```

Всё, что адресовано контейнеру и пришло не с его собственного моста,
отбрасывается — так Docker закрывает прямой доступ к адресам контейнеров в
обход опубликованных портов. Таблица `raw` идёт **до** conntrack, `nat` и
`filter`, поэтому все прежние попытки промахивались мимо: `access-control` в
unbound, политика `FORWARD`, правило в `DOCKER-USER` — все они ниже по течению,
и пакет до них не доживал.

Как это выяснилось — на случай похожего тупика. Сначала `tcpdump` на обоих
концах: пакет виден на `awg0` (`10.99.0.13.59415 > 172.29.172.254.53`) и не
виден на мосту. Значит теряется между ними. Дальше пробные правила-счётчики
вверх по цепочке: в `FORWARD` — ноль, в `nat PREROUTING` — ноль, и только в
`raw PREROUTING` счётчик показал пакеты. Ноль в `nat PREROUTING` и был ответом:
выше него только `raw`. Один `ACCEPT` перед запретом — и запрос сразу прошёл,
`status: NOERROR`.

**Решение владельца от 8 августа 2026: контейнер убран совсем.** Обойти запрет
можно было одним правилом, но это борьба с собственной защитой Docker:
восстанавливать его пришлось бы после каждой пересборки набора правил —
перезапуск демона, перезагрузка. Ровно тот класс хрупкости, который закрывался
соседним пунктом про накопление правил. А выгода мала: клиенты и так шлют
запросы на `1.1.1.1` **внутри** туннеля, местный провайдер их не видит — ради
чего резолвер и задумывался; свой добавил бы только сокрытие запросов от
Cloudflare.

Из установщика убраны контейнер, сеть `awg-dns-net` и подсеть `172.29.172.0/24`.
Этап 7 теперь **снимает остатки прежних установок**: у тех, кто ставил VSM до
этой правки, контейнер и сеть на машине есть, и удаление AmneziaWG их бы не
тронуло — установщик про них уже не знал бы.

### Правила фаервола контейнера накапливались — закрыто дедупом

Копился не только `MASQUERADE`, как считалось сначала. Entrypoint образа при
каждом старте добавляет **четыре** правила: `MASQUERADE` в `nat POSTROUTING`,
`-i awg0 -j ACCEPT` в `INPUT` и две штуки в `FORWARD`. Его `shutdown` снимает
`ip rule` и сам интерфейс, а правила — нет. На стенде накопилось 28 лишних.

Множит их не только переустановка: контейнер поднят с
`--restart unless-stopped`, и любой его самостоятельный перезапуск добавляет
комплект мимо установщика — проверено голым `docker restart`, набор удвоился.

**Первая редакция правки снимала все правила перед стартом контейнера и была
хуже, чем кажется.** Во-первых, закрывала только путь через установщик.
Во-вторых, между снятием и подъёмом нового комплекта узел оставался без NAT —
окно, ничем не покрытое.

Сейчас `dedupe_awg_rules` оставляет по одному экземпляру каждого правила и
зовётся **после приёмки**, когда демон уже подтвердил конфигурацию и правила
заведомо на месте. Раньше звать нельзя: `docker run` возвращает управление до
того, как entrypoint дошёл до `iptables`, и дедуп свернул бы старое в один
экземпляр, к которому контейнер тут же добавил бы свой. Снятие всех правил
(`prune_awg_rules`) осталось только в удалении, где контейнера уже нет — иначе
на машине навсегда остаётся `MASQUERADE` для подсети несуществующего туннеля.

Режим `--mode dedupe` вынесен наружу, меню зовёт его при входе.

Проверено на стенде: 28 правил свелись к 1/1/2, повторный прогон молчит,
трафик через туннель идёт — эталонный клиент в отдельном netns, пинг 3/3,
счётчик `MASQUERADE` перешёл с нуля на первый пакет соединения.

**Непокрытым остаётся один путь:** между визитами в меню цикл падений
контейнера по-прежнему добавляет по комплекту на попытку. Структурно это
чинится передачей NAT на нашу сторону — у образа есть `AWG_NAT=off`, тогда
правила ставим и держим мы сами, — но это смена схемы, и решение за владельцем.

### Три дефекта, найденных прогоном обеих версий

**Приёмка врала о провале.** Проверка `config-applied` была одноразовым грепом
по журналу сразу после того, как порт начал слушаться, — гонка по построению:
демон биндит сокет и пишет строку почти одновременно. Владелец поймал это на
переустановке 3.0 → 2.0: установка отработала, а приёмка объявила провал.
Теперь отказ (`config-rejected`) ищется первым и отдельно — он окончателен, — а
успех ждётся через `wait_until`.

**Занятость UDP-портов не проверялась вовсе.** `port_busy` читала для UDP поле
5 вывода `ss`, где лежит peer-адрес `0.0.0.0:*`, тогда как локальный адрес — в
поле 4. Автоподбор мог выдать занятый порт, а явно указанный занятый проходил
без слова. Поймано тестом, скормившим порт работающего же сервера.

**Отказы по порту не объясняли себя.** 443, 22 и опечатка давали одно и то же
«Порт невалиден», потому что общее правило «не ниже 1024» срабатывало раньше
частных проверок. Причину приходилось искать в коде.

### Переустановка не снимала записи пиров

Этап 6 генерирует новый приватный ключ сервера при каждой установке — значит все
ранее выданные конфиги мертвы, в них публичный ключ прежнего сервера. Об этом
установщик предупреждает и требует слово `ПЕРЕУСТАНОВИТЬ`.

А сами записи пиров жили в томе `awg-state` и переустановку переживали: том
снимал только режим `uninstall`. Последствия хуже, чем просто мусор. Entrypoint
восстанавливал их при старте, и сервер нёс пиров, которые физически не могут
подключиться. А `awg-peer add` под прежним именем отвечал `peer already exists`
— выдать клиенту рабочий конфиг под его же именем становилось нельзя, и человек
оставался без доступа при полностью исправном сервере.

Поймано владельцем на переустановке 3.0 → 2.0. Теперь том снимается в установке,
проверено: после перехода на 2.0 в томе ноль записей, у демона ноль пиров, конфиг
под прежним именем выдаётся.

Заодно исправлено, как выглядел этот отказ. «Конфиг ниже, сохраните его сейчас»
печаталось первым, а под ним оказывалось `peer already exists` — то есть отказ
выдавали за конфиг, и человек копировал сообщение об ошибке. Конфиг теперь
собирается до печати заголовка, код возврата разбирается, поток ошибок отделён от
вывода.

### Экран клиентов: список по именам и отзыв доступа

Выдать конфиг было можно, отозвать — нельзя. Причём и список не позволял: он
строился по `awg show`, а тот печатает одни публичные ключи. По такому списку не
понять, чей клиент, и уж точно не выбрать, кого удалять — экран был бесполезен
ровно тогда, когда нужен. Имена знает `awg-peer`, он их и хранит.

Удаление подтверждается `[y/N]` с показом отзываемой строки, а не вводом слова
целиком: словом подтверждаются операции, сносящие стек, здесь же отзывается
доступ одного клиента — вес как у удаления AdGuard. Имя сверяется со списком
**до** удаления: опечатка не должна молча ничего не сделать и оставить человека
в уверенности, что доступ отозван. Результат проверяется повторным чтением
списка, а не кодом возврата.

Проверено на стенде тремя путями: опечатка — отказ и клиент на месте; отмена по
`N` — клиент на месте; подтверждение — клиента нет ни в списке, ни у демона.

### Конфиг для mihomo собирает скрипт, а не человек

Дважды конфиг переносили в формат mihomo вручную, и дважды он выходил
нерабочим. Существенно то, что **ошибки были не в значениях, а в структуре**, и
каждая выглядела снаружи одинаково — «VPN не работает»:

| Ошибка | Как выглядела |
|---|---|
| обфускация на верхнем уровне вместо блока `amnezia-wg-option` | mihomo её просто не читает |
| `preshared-key` вместо `pre-shared-key` | ключ игнорируется |
| `dns-server` вместо `dns` | резолвер не задан |
| потерян `persistent-keepalive` | туннель поднимался, проходило несколько килобайт, счётчики вставали навсегда |

Последнюю поймали замером на сервере: рукопожатие есть, `transfer` не растёт
между двумя опросами с интервалом 20 с, захват на интерфейсе за 45 с — ноль
пакетов. Серверная сторона при этом была проверена полностью: форвардинг,
`MASQUERADE` с ненулевым счётчиком, `FORWARD` в обе стороны, маршрут наружу.

`awg2mihomo.sh` читает клиентский конфиг из файла или со стандартного ввода и
переносит поля сам. На конфиге **3.0 он отказывается работать** и объясняет
причину: выдать такой конфиг значит выдать заведомо нерабочий. В меню клиентов
два пункта выдачи — обычный формат и mihomo; пир создаётся один и тот же,
отличается только представление.

Проверено на стенде: вывод разбирается `yaml.safe_load`, значения `i1`-`i5`
читаются строками как есть, на конфиге 3.0 код возврата 1 и пустой stdout —
меню в этом случае печатает обычный формат, а не тишину.

### 3.0 понимают не все клиенты — и это не видно по конфигу

Поймано владельцем на живом клиенте: сервер 3.0, конфиг выдан, mihomo молчит,
пинга нет. Пиру ни одного рукопожатия.

Причина в `HeaderProtectionKey`. Он меняет формат пакета в проводе: заголовок
шифруется ChaCha20 с nonce из первых 12 байт S-паддинга. Клиент, который про
защиту заголовков не знает, не может ни разобрать чужой пакет, ни собрать свой
— рукопожатия не будет вовсе. Снаружи это выглядит как «сервер не отвечает», а
по конфигу причина не видна: все привычные параметры на месте.

**mihomo и clash-meta знают AmneziaWG до 2.0 включительно** — `jc/jmin/jmax`,
`s1-s4`, `h1-h4`, `i1-i5`. Полей `header-protection-key` и
`content-padding-addition` у них нет; проверено по их документации. То же
касается XKeen, который использует mihomo. Официальные клиенты AmneziaVPN и
`amneziawg-tools` из `ppa:amnezia/ppa` 3.0 понимают — последнее мы сами
проверяли эталонным клиентом в netns.

Меню теперь говорит это на экране выбора версии, до установки. Прежде оно
предлагало 3.0 первым пунктом и молчало о совместимости.

**Побочная находка того же разбора.** В присланном конфиге строки `I1`–`I5`
выглядели пустыми, и это чуть не увело в ложный след. Проверка на стенде
показала, что выдаются они непустыми — 97, 63, 61, 45 и 62 символа. Пропали
они при пересылке: значение начинается с `<b 0x…>`, и разметка съела это как
HTML-тег. Вывод на будущее: конфиг, пришедший через мессенджер или чат,
сверять с тем, что реально печатает `awg-peer`, а не разбирать как есть.

### Совпадение длин служебных пакетов — чинится у нас

Найдено при разборе `bivlked/amneziawg-installer`, куда владелец отправил за
сравнением. Автор того установщика выписал по исходникам модуля ядра размеры
служебных сообщений: init 148, response 92, cookie reply 64. S-паддинг
прибавляется к ним, поэтому три пары способны совпасть по длине в проводе:
`S2 = S1 + 56`, `S3 = S2 + 28`, `S3 = S1 + 84`.

Совпадение туннель не ломает — демон конфиг принимает и работает. Но два
разных типа служебного пакета получают одинаковую длину, и DPI различает их по
ней: теряется ровно то, ради чего S-паддинг задаётся. Тихий дефект, наружу
никак не проявляется.

`awg-tool` этого не проверяет. Замер на стенде, 600 наборов по 300 на версию:
`S3 = S2 + 28` встретилось 6 раз, около 1%. Две другие пары не встретились ни
разу — при нынешних диапазонах они недостижимы, но проверяются всё равно:
диапазоны чужие и могут поменяться. Фильтр с перегенерацией добавлен в
`awg-stack.sh`; проверен фактом — 300 прогонов через него, сработал 5 раз,
коллизий не осталось ни одной.

**Вторая половина той же проверки дефекта не нашла.** При включённой защите
заголовков все `S1`-`S4` обязаны быть не меньше 12: nonce для ChaCha20 нигде не
передаётся, а берётся из первых 12 байт S-паддинга, и модуль отвечает
`-EINVAL`. Была версия, что `awg-tool` про это не знает и часть установок 3.0
не поднимется. Не подтвердилось: на 300 наборах 3.0 минимум по каждому `S`
равен ровно 12, тогда как на 2.0 — 4. Ограничение учтено автором.

**Риск источника назван вслух:** проект создан 2026-07-28, на момент внедрения
14 звёзд. Отсюда жёсткий пиннинг — релиз `awg-tool` со сверкой официальной
sha256 и оба образа по digest.

### Три дефекта чужой конфигурации, обойдённые у нас

1. **Пример автора роняет резолвер.** Образ стартует от root, а `unbound.conf`
   требует сброса привилегий на пользователя `unbound`, что при `cap_drop: ALL`
   невозможно: восемь падений подряд. Возвращены ровно `SETUID` и `SETGID`.
2. **`--sysctl` несовместим с `--network host`** — Docker отвергает запуск.
3. **После перезагрузки `ip_forward=0`**, при этом контейнеры подняты и порт
   слушает: узел выглядит исправным, а маршрутизировать трафик нечем. Пишем
   постоянную запись в `/etc/sysctl.d/` и переводим `DEFAULT_FORWARD_POLICY` в
   `ACCEPT`, иначе включение UFW обрежет FORWARD.

### Host-режим, а не публикация порта — по измерению

При `-p` пакет доходит до контейнера через DNAT даже когда UFW активен и
правила для порта нет: Docker его обходит. Тогда меню UFW показывало бы порт
закрытым, пока он открыт. В host-режиме порт слушает сам демон, и UFW им
управляет. Обе стороны проверены на стенде.

### Чего у этого решения нет

**Контейнер непригоден в роли клиента:** его entrypoint кладёт `fwmark` в
секцию пира, тогда как в UAPI это ключ интерфейса — `errno=-22`. Проявляется
только при `AllowedIPs = 0.0.0.0/0`. На роль сервера не влияет, но проверить
полный туннель их же контейнером нельзя; выход наружу подтверждён обходным
путём — клиенту выдавался маршрут на один адрес.

**Конфиг проверен эталонной реализацией.** GUI-приложение AmneziaVPN запустить
негде, но есть проверка ближе к делу: официальные `amneziawg-tools` и модуль
ядра из `ppa:amnezia/ppa`. Клиент поднят в отдельном netns (иначе маршрут
`10.99.0.0/24` сталкивается с сервером на той же машине, а имя `awg0` занято
сервером в host-режиме).

Результат: `awg setconf` принял конфиг целиком, и эталонный `awg show` показал
**все** ключи 3.0 — `i1`–`i5`, `header protection key`,
`content padding addition`, `rekey after time`, `reject after time`,
`max handshake attempts`. Рукопожатие состоялось, пинг 3/3 без потерь.

То есть выдаваемые нами конфиги работают не только с контейнером автора, но и
с официальной реализацией протокола. Само GUI-приложение по-прежнему не
проверялось — оно использует ту же библиотеку, но это уже вывод, а не замер.

### Разрушающие пункты — прогнаны на стенде 8 августа 2026

До этого не запускались ни разу: снос стека, панели, ботов, удаление AmneziaWG.
Владелец дал добро на стенде.

**Защита держит.** Шесть подтверждений проверены вводом НЕВЕРНОГО слова:
удаление панели, удаление стека, полная установка стека (она стирает 3x-ui),
удаление ботов, удаление AmneziaWG, переустановка AmneziaWG. Во всех шести —
«Отменено», и снимок состояния (четыре службы, контейнер, юниты ботов) до и
после совпал побайтно.

**Удаление AmneziaWG** — чисто: ноль контейнеров, ноль правил фаервола, конфиг,
каталог и запись sysctl сняты, стек не тронут.

**Удаление стека telemt** — юниты сняты, маска из `conf.d` убрана, блок доступа
к панели вычищен из vhost, nginx и x-ui остались подняты, сертификаты целы.

**Два дефекта, найденных этим прогоном.** Оба — показ секретов уже
несуществующей службы, и оба видны только ПОСЛЕ удаления, то есть в состоянии,
которого раньше никто не создавал:

1. Пункт 0 показывал логин и пароль удалённой панели telemt. Причина:
   `/etc/vsm/telemt.conf` переживает снос стека (там же домены, и это
   осмысленно для повторной установки), а экран доступов читал учётки прямо из
   файла.
2. Он же показывал **адрес** удалённой панели вместе с секретным префиксом —
   тот же дефект, замеченный на шаг позже, когда первый уже был исправлен.

Теперь признак установки проверяется один раз на весь блок.

**Удаление панели откатывает пересборку nginx.** Оно вычищает пакет `nginx`
целиком, а вместе с ним уходит сборка с OpenSSL 3.5 — постквантовый обмен
после этого не согласуется. Проверено сразу после пересборки стека: отпечаток,
протокол, шифр, группа и ALPN у маски и панели совпали, а `X25519MLKEM768` не
согласован ни на 7444, ни на 443. Это не дефект, а следствие, но экран
подтверждения о нём молчит — говорит только про пакет и каталог. После сноса
панели пересборку надо запускать заново, пункт «Пересборка nginx».

**Полная сборка стека с нуля прогнана после всех правок сессии** — на
сохранённых доменах и уцелевших сертификатах Let's Encrypt. Четыре службы
поднялись, маска на месте, инвариант «маска ≡ панель» подтверждён штатным
пунктом «Сверить TLS».

**Цена, которую стоит знать заранее: удаление ботов уносит токены.**
`/etc/vsm/bots.conf` и `bots/.env` снимаются оба, а токен нигде больше не
хранится. Восстановить ботов без токена от @BotFather нельзя, и экран
подтверждения об этом не предупреждает — говорит «Службы, окружение, данные
карты». Это стоит дописать.

### Обработчики второго уровня и все четыре режима ботов — прогнаны

**Двадцать экранов второго уровня** открыты и проверены на ошибки оболочки.
Это то, что оставалось непроверенным после переделки оформления: она шла по
главным экранам, а `clear 2>/dev/null` был прогнан слепым `sed` по девяти
файлам — то есть обработчики трогали, но не открывали.

Находка одна: **смена порта WARP не проверяла ни установку, ни результат**. На
сервере без WARP пункт вываливал сырое `warp-cli: command not found` и следом
печатал `✅ Порт: …`. Шестой случай того же класса — рапорт об успехе поверх
ничего не сделанного. Соседние пункты проверку установки делают, этот забыл.

**Режим «два отдельных бота» проверен наконец** — он оставался непроверенным с
самого начала, потому что для него нужны два токена.

Замер с одним токеном в обоих слотах даёт точный ответ, чего именно не хватало:
установщик отрабатывает целиком — оба юнита созданы, оба запущены, конфиг
записан, — а вот работать они не могут. Telegram отдаёт `TelegramConflictError`
каждые пять секунд обоим процессам. **Инвариант 8 подтверждён замером**, а не
чтением: два опросчика на один токен несовместимы по устройству Telegram, и
второй токен здесь не удобство, а требование.

Оба одиночных режима проверены тем же токеном по очереди и работают: `telemt-bot`
опрашивает API telemt (`200 OK` раз в минуту), `3xui-bot` поллит Telegram как
`@adkrw3xuibot`. Переключение между режимами снимает юниты прежнего — взаимное
исключение держит.

### Что НЕ проверено

- Режим ботов «два отдельных бота» — нужен второй токен Telegram.
- Разрушающие пункты: удаление стека, удаление панели, удаление ботов.
- Меню тестов (censorcheck, YABS, iPerf3, sysbench, сканеры), утилиты, WARP.
- Пункты X-UI: патч, AdGuard, бэкап и восстановление.
- MTProxyL — установка и режим Reanimator.
- SSL-меню: выпуск сертификата и реальный Ctrl+C для проверки `trap`
  (осторожно с лимитами Let's Encrypt).

Вывод, который стоит держать в голове: **проверять результат фактом, а не кодом
возврата предыдущего шага**.

### Что уже пробовали — не повторять

| Попытка | Почему не сработала |
|---|---|
| `tr -d '\0'` для очистки вывода `openssl s_client` | Ломает разбор: перестают находиться `Protocol` и `Cipher`. Решение — временный файл |
| Захват вывода `s_client` в переменную | Нулевые байты, bash предупреждает и портит поля |
| Артефакт PQ nginx от MTProxyL | Нет модуля `stream` |
| Теория «маска отличима по шифрам» | Измерением не подтвердилась: vhost панели задаёт те же значения, что были захардкожены. Зеркалирование всё равно полезно как устойчивость, но живой дырой это не было |
| `pkill -f "<шаблон>"` при работе с меню через pty | Убивает собственную ssh-сессию, если шаблон совпадает |
| Обрезание лога живой сессии `script` | `script` держит offset, файл читается как нули |
| `[[ условие ]] && присваивание` под `set -e` | Ложное условие возвращает 1 и роняет скрипт. В проекте принята полная форма `if/fi` |
| `CODE="$(curl ...)"` под `set -e` | Падает раньше строки с `die`, причина не видна. Нужен `|| true` |

### Особенности окружения разработки

- **Windows + git-bash:** `chmod` и `umask` — no-op, `stat` всегда показывает
  644. Права проверяются только на Linux.
- **`python`/`python3` на Windows** могут быть заглушками Microsoft Store —
  печатают «Python» и выходят с ненулевым кодом. Python-код проверять на сервере.
- **Прогон интерактивных меню без TTY:**
  ```bash
  printf '4\n\nX\n' | timeout 180 bash menu_telemt.sh 2>&1 | sed 's/\x1b\[[0-9;?]*[a-zA-Z]//g'
  ```
  `timeout` обязателен: при EOF цикл меню крутится вечно.
- **Длинные операции** запускать через `nohup setsid ... > /tmp/x.log 2>&1 &` и
  опрашивать лог.

## 7. Соглашения проекта

**Комментарии объясняют «почему», а не «что»** — как правило, описывают дефект,
который уже случался. Это не украшение, а способ не наступить второй раз.

**Коммиты** — Conventional Commits, тема и тело на русском, тело объясняет
причину и последствия. В конце строка `Co-Authored-By: Claude Opus 5
<noreply@anthropic.com>`.

**Разрушающие операции** подтверждаются вводом слова целиком (`СТЕРЕТЬ`,
`УДАЛИТЬ`), регистр учитывается. При добавлении пунктов меню разрушающий сдвигать
только **от** привычной позиции, никогда к ней.

**Оформление меню — через примитивы `ui_*`**, а не литералами. Перед коммитом
правок в меню запускать `bash check-ui.sh`: он ловит три класса дефектов,
которые не видны ни в `bash -n`, ни в диффе, — эмодзи с вариационным
селектором, цвет в обход палитры и подпись длиной ровно в ширину своей колонки.
За один заход по девяти файлам эти три нашлись шесть раз, и каждый раз — уже
после коммита, в живом терминале.

**Проверка вида — глазами в SSH-сессии.** `bash -n` проверяет синтаксис, а не
вёрстку; дифф показывает изменение строки, а не то, как она ляжет. Узкий экран
проверяется через `VSM_COLS=<n>`: при выводе в пайп `tput` отвечает не шириной
окна, а значением из terminfo, и проверка молча проходит на восьмидесяти
колонках.

**Рабочий цикл:** правка → код-ревью → коммит → пуш в `main`. На сервере
обновление — `git -C /root/VSM pull origin main`; при добавлении новых файлов
ещё и `bash /root/VSM/install.sh` для пересоздания симлинков.

> **Важно:** новый файл модуля обязан попасть в git с битом исполнения
> (`git update-index --chmod=+x`). `install.sh` делает `chmod +x`, и файл,
> закоммиченный как `100644`, ломает `git pull` у всех, кто уже поставил VSM.

## 9. С чего начать

```bash
git clone https://github.com/adkudryashov/VSM.git && cd VSM
git log --format='%h %s' -25          # работа последней сессии
cat docs/CODEMAPS/architecture.md     # устройство и инварианты
```

Первая задача — прогнать починенную пересборку на живом сервере. Код готов и
проверен на заглушках, но настоящей сборкой не подтверждён (раздел 3):

```bash
DRY_RUN=1 bash rebuild-nginx-openssl35.sh   # решения отбора, система не тронута
nohup setsid bash rebuild-nginx-openssl35.sh > /tmp/rebuild.log 2>&1 &
```

Итог принимать только по фактам: `nginx -V` показывает OpenSSL 3.5.6,
`/opt/openssl-3.5/bin/openssl version` запускается, пять служб `active`,
отпечатки на порту маски и 443 совпадают со слепком, а пункт 5 «Сверить TLS
маски и панели» даёт PQ на **обоих** портах.

Перед любыми изменениями на сервере снять слепок:

```bash
ss -ltn > /root/ports-before.txt
systemctl is-active nginx x-ui telemt telemt-panel
```

И держать в голове главный критерий целости — **совпадение отпечатка
сертификата и ALPN между портом маски и портом 443**. Проверяется пунктом
«Сверить TLS маски и панели» или вручную:

```bash
D=<домен панели>
for p in <порт маски> 443; do
  echo | openssl s_client -connect 127.0.0.1:$p -servername $D 2>/dev/null \
    | openssl x509 -noout -fingerprint -sha256
done
```

Отпечатки обязаны совпасть побайтно.
