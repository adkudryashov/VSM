# Как здесь принято работать

Этот документ — не формальность и не список пожеланий. Почти каждое правило
ниже появилось после конкретного дефекта, и рядом написано, какого именно.
Читать стоит целиком: он короче, чем время, которое уходит на повторение
чужой ошибки.

---

## Главное правило

> **Проверять результат фактом, а не кодом возврата предыдущего шага.**

Класс дефектов, встреченный в этом проекте чаще любого другого, — **рапорт об
успехе поверх сломанной системы**. Он опаснее честного отказа, потому что
создаёт уверенность, что всё работает.

Живые примеры, каждый пойман уже после коммита:

| Что рапортовало об успехе | Что было на самом деле |
|---|---|
| «✅ Панель доступна» | Панель отдавала 404: проверялся код возврата применения конфига, а не ответ |
| `update_geoip.sh` возвращал 0 всегда | Последней командой стоял `echo` |
| «Всегда включать IPv6» | `::1` оставался отключённым |
| Скрипт резервной копии 3x-ui | Превращался в пустышку при обрыве загрузки |
| Снятие блока nginx | Функция звалась без обязательного аргумента, ничего не делала и возвращала ноль |
| Отправка тревоги в Telegram | `curl` без `--fail` возвращает ноль и на `400`, и на `401` |

Отсюда практика: после починки **перечитать то, что чинили**, и сравнить с
ожидаемым. Именно так устроены `checks/drift.sh` и `tools/vsm-backup.sh`.

## Проверки перед коммитом

Четыре команды, все обязаны быть зелёными. Их же гоняет CI при каждом пуше:

```bash
python -m pytest tests/ -q     # логика ботов и сторожа, без сети и сервера
bash checks/shell.sh           # ShellCheck, порог — ноль замечаний
bash checks/ui.sh              # оформление меню
bash checks/drift.sh --dry-run # сверка с реестром решений (только на сервере)
```

`checks/drift.sh` в CI не запускается: он сверяет живой сервер с реестром и на
чистой машине сборщика проверять ему нечего.

Зависимости для тестов ставятся отдельно и в боевую установку не идут:

```bash
python -m pip install -r bots/requirements.txt -r bots/requirements-dev.txt
```

### Порог ShellCheck — ноль, и это принципиально

Проверка с накопленным долгом бесполезна: два десятка «известных» замечаний
никто не читает, и новое настоящее теряется среди них в первый же день. Всё
неприменимое разобрано поштучно в [`.shellcheckrc`](.shellcheckrc) с
объяснением на каждый код. Если ваше замечание тоже неприменимо — **разберите
его и допишите туда**, а не глушите комментарием в коде.

## Комментарии

**Объясняют «почему», а не «что».** Как правило, описывают дефект, который уже
случался. Это не украшение, а способ не наступить второй раз.

```bash
# ПЛОХО
# Проверяем, что файл существует
[ -f "$conf" ] || return 1

# ХОРОШО
# Отсутствие конфига — не ошибка: на установке без ботов его и не бывает.
# Прежняя версия здесь падала и уводила за собой весь установщик.
[ -f "$conf" ] || return 0
```

Если комментарий пересказывает код — его лучше удалить. Если объясняет
неочевидное решение или прошлую поломку — он ценнее самого кода.

## Коммиты

[Conventional Commits](https://www.conventionalcommits.org/), тема и тело на
русском. **Тело объясняет причину и последствия**, а не перечисляет изменённые
строки — их видно в диффе.

```
fix(drift): не считать пропажей блок nginx, когда панели нет вовсе

Позиция nginx_blocks проверяла наличие блока, ведущего на панель, но не
проверяла, установлена ли сама панель. Прогон удаления на стенде это вскрыл:
сняли обе панели — и позиция немедленно объявила расхождение на совершенно
исправной системе. Ровно тот ложный сигнал, после которого перестают верить
всей проверке.

Проверено обе стороны: панелей нет — «компонент не установлен»; панель есть,
а блока нет — расхождение с точным «стало/должно».
```

Хорошее тело коммита отвечает на три вопроса: **что было не так**, **почему
так вышло** и **чем доказано, что теперь верно**.

## Разрушающие операции

- Подтверждаются **вводом слова целиком** (`СТЕРЕТЬ`, `УДАЛИТЬ`, `ДА`), регистр
  учитывается. Не `[y/N]`.
- Перед необратимым — резервная копия (`tools/vsm-backup.sh`).
- В меню разрушающий пункт двигать **только от** привычной позиции, никогда к
  ней: мышечная память быстрее чтения.
- После удаления — **проверить фактом**, что удалилось, и не продолжать, если
  нет.

## Оформление меню

Только через примитивы `ui_*` из [`lib/ui.sh`](lib/ui.sh), не литералами.
Перед коммитом правок в меню:

```bash
bash checks/ui.sh
```

Он ловит три класса дефектов, невидимых ни в `bash -n`, ни в диффе:

1. **эмодзи с вариационным селектором** (U+FE0F) — терминал считает ширину
   иначе, и колонки разъезжаются;
2. **цвет в обход палитры** — ломает `NO_COLOR` и тему;
3. **подпись длиной ровно в ширину колонки** — на узком экране наезжает на
   соседнюю.

За один заход по девяти файлам эти три нашлись шесть раз, и каждый раз — уже
после коммита, в живом терминале.

**Вид проверяется глазами в SSH-сессии.** Узкий экран — через `VSM_COLS=<n>`:
при выводе в пайп `tput` отвечает не шириной окна, а значением из terminfo, и
проверка молча проходит на восьмидесяти колонках.

## Права на файлы

> Новый файл модуля обязан попасть в git **с битом исполнения**:
> `git update-index --chmod=+x путь`

`install.sh` делает `chmod +x`, но это лишь страховка: файл, закоммиченный как
`100644`, ломает установку у всех, кто уже поставил VSM. Библиотеки в `lib/`,
наоборот, исполняемыми быть **не должны** — их сорсят. CI проверяет и то, и
другое.

## Окружение разработки

Разработка ведётся с Windows, проверка — на сервере. Отсюда особенности:

- **`chmod` и `umask` в git-bash — no-op**, `stat` всегда показывает `644`.
  Права проверяются только на Linux.
- **`python`/`python3` на Windows** могут быть заглушками Microsoft Store:
  печатают «Python» и выходят с ненулевым кодом. Python-код проверять на
  сервере.
- **Переводы строк** закрыты `.gitattributes` (`* text=auto eol=lf`). Не
  копируйте файлы на сервер через `scp` из рабочей копии Windows — утащите
  CRLF и получите `bad interpreter: /bin/bash^M`. Штатный путь — `git pull`.
- **Прогон интерактивных меню без TTY:**
  ```bash
  printf '4\n\nX\n' | timeout 180 bash menus/telemt.sh 2>&1 | sed 's/\x1b\[[0-9;?]*[a-zA-Z]//g'
  ```
  `timeout` обязателен: при EOF цикл меню крутится вечно.
- **Длинные операции** — через `nohup setsid ... > /tmp/x.log 2>&1 &` с опросом
  журнала.

## Что уже пробовали — не повторять

| Попытка | Почему не сработала |
|---|---|
| `tr -d '\0'` для очистки вывода `openssl s_client` | Ломает разбор: перестают находиться `Protocol` и `Cipher`. Решение — временный файл |
| Захват вывода `s_client` в переменную | Нулевые байты, bash предупреждает и портит поля |
| `pkill -f "<шаблон>"` при работе с меню через pty | Убивает собственную ssh-сессию, если шаблон совпадает |
| Обрезание лога живой сессии `script` | `script` держит offset, файл читается как нули |
| `[[ условие ]] && присваивание` под `set -e` | Ложное условие возвращает 1 и роняет скрипт. Принята полная форма `if/fi` |
| `CODE="$(curl ...)"` под `set -e` | Падает раньше строки с `die`, причина не видна. Нужен `\|\| true` |
| `perl -pi -e` с `$(` или `${...}` в строке замены | Подставляет свои переменные. Для таких замен — только точечная правка файла |
| Кириллица в именах переменных bash | `local ответ` — не идентификатор, присваивание рушится молча |
| Одинаковый порт для двух панелей вместо явной проверки | Делает замену невозможной и превращает конфликт в «address already in use» из глубины чужого установщика |

## Рабочий цикл

```
правка → проверки локально → коммит → пуш в main → CI
```

На сервере обновление — `git -C /root/VSM pull origin main`. При добавлении
новых файлов ещё и `bash /root/VSM/install.sh` для пересоздания симлинков.

Отдельных веток поддержки нет: проект живёт в `main`.

---

## Чего делать не нужно

- **Фиксировать версии сторонних компонентов.** Это отрезает и исправления
  безопасности. Вместо этого запоминается отпечаток чужого установщика
  (`lib/deps.sh`), а изменения в их настройках ловит `checks/drift.sh`.
- **Молча возвращать общесистемные настройки.** Реестр решений делит позиции
  на два класса: незаметность и безопасность чинятся молча, всё остальное
  показывается и ждёт человека. Журналирование, права sudoers, чужие таймеры —
  всегда второй класс.
- **Считать зелёный CI готовностью к бою.** Он проверяет модули и скрипты, а
  «клиент подключился через прокси» не проверяет ничто.
